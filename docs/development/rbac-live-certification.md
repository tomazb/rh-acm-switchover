# Live RBAC Bootstrap Certification

This document describes how to run the live RBAC bootstrap certification
scenario, which validates that the ACM Switchover RBAC manifests grant the
correct end-to-end permissions on a real or disposable cluster.

## Background

The regular `rbac-bootstrap` release scenario only verifies static manifest
parity: it plans which manifests to apply and writes a dry-run summary but
does **not** connect to a cluster.  The *live RBAC certification* scenario
adds the missing end-to-end layer: it runs `SubjectAccessReview` checks
against an actual cluster where the RBAC manifests have already been applied,
proving that all required permissions are granted.

## Scope

The live certification validates the following flows:

| Flow | Key permissions checked |
|------|-------------------------|
| Normal switchover | `managedclusters` patch, `backupschedules` patch, `restores` create, Thanos StatefulSet/Deployment patch |
| Old-hub finalization | `multiclusterobservabilities` **delete** (required when finalization tears down MCO on the old hub) |
| Decommission (opt-in) | `managedclusters` delete, `multiclusterhubs` delete, `multiclusterobservabilities` delete |
| Validator role | All permissions read-only, no write verbs |

The critical MCO `delete` permission is tested both in the old-hub
finalization flow and in the optional decommission flow.

## Static vs. live checks

| Check type | Trigger | Cluster required |
|------------|---------|-----------------|
| Static RBAC parity (`test_rbac_integration.py`) | Normal `pytest tests/` run | No |
| Dry-run bootstrap (`rbac-bootstrap` release scenario) | `--release-profile` | No |
| **Live RBAC certification** (this document) | `ACM_ENABLE_LIVE_RBAC_CERTIFICATION=1` | **Yes** |

## Prerequisites

Before running the live certification:

1. **Apply the RBAC manifests** on the target cluster:

   ```bash
   # Kustomize
   kubectl apply -k deploy/kustomize/base/ --context <ctx>

   # or Helm
   helm install acm-switchover-rbac deploy/helm/acm-switchover-rbac/ \
     --kube-context <ctx>

   # or the bootstrap script (generates kubeconfigs too)
   ./scripts/setup-rbac.sh \
     --admin-kubeconfig <admin-kubeconfig> \
     --context <ctx> \
     --include-decommission
   ```

2. **Apply the opt-in decommission ClusterRole** if you want to validate
   decommission and finalization permissions:

   ```bash
   kubectl apply -f deploy/rbac/extensions/decommission/ --context <ctx>
   ```

3. **Obtain the service-account kubeconfig** generated by the bootstrap step.
   The SSAR checks must run as the *service account*, not as cluster-admin.

   ```bash
   # The setup-rbac.sh script writes kubeconfigs to the --output-dir
   export KUBECONFIG=<output-dir>/operator-kubeconfig.yaml
   ```

## Running the pytest live certification

```bash
# Minimal – uses the active kubeconfig context
ACM_ENABLE_LIVE_RBAC_CERTIFICATION=1 \
  pytest tests/test_rbac_live_certification.py -v -m live_rbac_certification

# Explicit context
ACM_ENABLE_LIVE_RBAC_CERTIFICATION=1 \
ACM_LIVE_RBAC_CONTEXT=my-disposable-hub \
  pytest tests/test_rbac_live_certification.py -v -m live_rbac_certification

# Specific flow only
ACM_ENABLE_LIVE_RBAC_CERTIFICATION=1 \
  pytest tests/test_rbac_live_certification.py::TestLiveOldHubFinalizationPermissions -v
```

All tests are skipped when `ACM_ENABLE_LIVE_RBAC_CERTIFICATION` is not set,
so they never interfere with ordinary `pytest tests/` runs.

## Running via the release profile (Ansible stream)

The `live-rbac-certification` scenario is an optional, non-required entry in
the release scenario catalog.  It is Ansible-only and runs the
`live_rbac_certification.yml` playbook, which re-uses the `rbac_bootstrap`
role with `validate_permissions: true`, `include_decommission: true`, and
`include_old_hub_finalization: true`.

### Cluster assumptions for the Ansible scenario

* The cluster context supplied via `acm_switchover_hubs.primary` must have the
  RBAC manifests and the decommission extension **already applied**.
* The kubeconfig supplied must belong to a user with permission to run
  `SubjectAccessReview` (typically cluster-admin or a user with
  `authorization.k8s.io/subjectaccessreviews: create`).
* The cluster is disposable or explicitly approved for this operation.  No
  managed clusters or ACM components will be modified; only SAR API calls are
  made.

### Adding to a release profile

```yaml
# in your release profile YAML
scenarios:
  - id: live-rbac-certification
    streams:
      - ansible
```

Then run:

```bash
pytest tests/release/ -m release \
  --release-profile <path-to-profile.yaml> \
  --release-scenario live-rbac-certification
```

## Environment variables

| Variable | Default | Description |
|----------|---------|-------------|
| `ACM_ENABLE_LIVE_RBAC_CERTIFICATION` | _(unset)_ | Set to `1`, `true`, or `yes` to enable live pytest tests |
| `ACM_LIVE_RBAC_CONTEXT` | _(active context)_ | Kubernetes context to use for SSAR checks |

## Safety guarantees

* **No writes**: All checks use `SelfSubjectAccessReview` (pytest path) or
  `SubjectAccessReview` (Ansible path), which are read-only from the
  perspective of the cluster's workloads.
* **No managed cluster contact**: Only the primary hub context is used.
* **Skipped by default**: Both the pytest tests and the Ansible scenario
  require explicit opt-in; they are never part of default test runs.

## Troubleshooting

### "Could not connect to cluster context"

The kubeconfig or context name is wrong, or the cluster is unreachable.
Check with `kubectl cluster-info --context <ctx>`.

### Permissions denied

1. Verify the RBAC manifests were applied: `kubectl get clusterrole acm-switchover-operator`.
2. Verify the decommission extension is applied when testing decommission/finalization:
   `kubectl get clusterrole acm-switchover-decommission`.
3. Verify you are using the service-account kubeconfig, not cluster-admin.

### Test skipped unexpectedly

Confirm `ACM_ENABLE_LIVE_RBAC_CERTIFICATION=1` is exported in the shell
that runs pytest.
